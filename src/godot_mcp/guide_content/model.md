# Model: editor, disk, runtime, and resource identity

Godot MCP works across three related states. The editor state is the live scene tree, inspector values, scripts, selections, and unsaved buffers held by the open Godot editor. Disk state is the authored project files that have been saved. Runtime state is a launched game process and its scene tree at a particular run. A successful change in one state does not automatically prove the others match: a source edit can remain an unsaved draft, a saved source can still need an editor reload, and a running game can continue executing the source snapshot it started with.

Use `read_scripts` to establish the editor source you are about to change. Each returned document has a `revision`; the response also provides `base_revisions` and an `editor_epoch`. Supply the returned revision for an updated URI in `apply_script_changes`. Exact context and retained read bases allow independent concurrent edits to merge, while overlapping or ambiguous changes become conflicts and make no source change. A source revision identifies the editor document state; it is not a claim that the file is saved or that the running game uses it.

`apply_script_changes` coordinates source application, optional source saves, editor reload, attachments, and signal connections. Its `save` option defaults to false, so live changes may remain drafts. Explicit validation is a separate `get_diagnostics` request. `run_scene` can save an explicit `save_uris` set first, then starts from a startup snapshot covering the launch scene, autoloads, and declared dependencies. Runtime tools identify observations with a `run_id`; use `inspect_runtime`, captures, conditions, or performance sampling to assess what the game actually did. Source provenance can report `matches_startup` or `source_changed`, but file identity never proves behavior.

Editor node references contain a scene URI and a path relative to its root, such as `{ "scene": "res://main.tscn", "path": "Player" }`. The root path is `.`. Use returned references; renaming or reparenting can change paths. Runtime references carry a run identifier and an absolute runtime path, for example `{ "run_id": "...", "path": "/root/Main" }`. A live node reference can be used as the `duplicate` source for node creation. Runtime handles and debugger frame handles are tied to their run or pause state; a frame handle becomes stale after continue.

Resource selectors deliberately distinguish a project resource URI from a node property. A selector is exactly one of `{ "uri": "res://material.tres" }` or `{ "node": { "scene": "res://main.tscn", "path": "Sprite", "property": "material" } }`. Resource URIs may also be returned as `godot://resources/...` handles. For mutations that require scope, choose exactly one `local` node target or `shared` resource target. Local scope changes the property value belonging to that node. Shared scope changes the reusable resource itself and may affect every owner. Read users and import provenance before choosing shared scope.

Values in properties, animation keys, input conditions, and other mutation fields are JSON values or tagged Godot values. The catalog describes tagged values with a `$type` and named components. For example, a color can be supplied as `{ "$type": "Color", "r": 1, "g": 0.5, "b": 0, "a": 1 }`; color space is `linear` or `srgb` where the value representation exposes it. Resources use a returned URI rather than an arbitrary serialized object. Named choices such as an input action (`{ "action": { "action": "ui_accept", "pressed": true } }`) make the intended Godot variant explicit.

Authored and imported data have different ownership. Authored documents can be persisted with `save_documents`. Imported resources are managed by Godot's import pipeline and are excluded from authored dirty-save and run requirements. To edit an imported shared resource, detach or export it with `save_as` to create an authored copy; the imported source remains unchanged. `create_resource` can make an in-memory resource, optionally assign it to a node property, or save it under an authored URI.

Bindings are explicit. A script attachment names a source URI and node reference. A shader attachment names a source URI and an explicitly scoped ShaderMaterial target. Signal `connect` and `disconnect` records name `from`, `signal`, `to`, `method`, and optional binds. These editor relationships are reported separately from source validation and follow the operation's binding phase.
