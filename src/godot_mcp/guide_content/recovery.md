# Recovery: pending work, conflicts, and durable restoration

Mutation responses distinguish work that is still running from work that is blocked. `status: "pending"` means an operation is still running and includes an `operation_id`; query it for detailed phases and items. A blocked source continuation has stopped at a recoverable point and needs a repair or prerequisite. A partial result records effects already applied and observations that failed. Do not submit the same mutation again merely because its initial wait timed out.

For any retained operation, call `get_operation_result` with its `operation_id` and optionally `wait_ms` (bounded by the tool schema). This waits for the same work and returns the operation-time snapshot plus current resume and Undo state. It does not replay the patch, save, import, or input. `get_context` with `scope: "progress"` is the compact status path for other editor activity. When the editor is busy, the error reports the active tool, phase, elapsed time, and operation ID when available; follow the retained operation or inspect progress instead of starting a competing mutation.

Source changes that stop in a blocked phase continue with `resume_script_changes`. The continuation preserves completed saves and successful bindings and does not replay the patch. If you repaired a source, provide a current read revision for every original source in `revisions`; accepting those revisions repeats only the required source saves and reloads. Changes made to a target while the operation was blocked still produce a conflict. Overlapping edits, stale revisions, unknown disk baselines, and external changes are guarded conditions: resolve the current text or disk state, read again, and submit an intentional patch rather than assuming the old base is safe.

One source operation can apply effects in phases: source, `save_sources`, `editor_reload`, bindings, and `save_bindings`. A later reload or binding failure does not erase source changes already applied, and saved source remains on disk. A deferred reload returns `RELOAD_DEFERRED` and can be continued, but Godot may auto-reload independently. This is why a failure receipt must be read per document and per phase. A failed source write prevents later dependent saves, while requested edits may remain available as unsaved changes. Saving is not a filesystem-wide atomic transaction.

Timeouts and connection loss require observation before retry. `send_input` may have processed some or all events before a condition wait or capture fails; its `processed`, `held_inputs`, stage results, and failures describe the effect. Retry the failed observation or capture rather than replaying the input sequence. An interrupted native save has an unknown disk outcome until the actual file contents are inspected. Connection loss never automatically replays a mutation. Imports and asset deletion similarly report applied, remaining, pending, and failed items; partial effects are possible.

Saving has explicit scope. `save_documents` persists the listed authored documents and processes source files before dependent scene or resource saves. If saving a scene could include other edited authored documents, the operation returns `SAVE_SCOPE_REQUIRED` and identifies the additional URIs; pass the intended complete set explicitly. Imported data is not made authored by saving it: use `save_as` to export an authored copy. To save before launch, list the documents explicitly in `run_scene.save_uris`; remaining unsaved authored documents block startup, while imported data is excluded.

Undo is an editor-history action, not a durable disk backup. `undo_edit(edit_id)` invokes native editor Undo and is guarded by the current Undo order; it refuses when another native editor action intervened. Saving a source does not make Undo restore the saved disk file. Recoverable asset deletion is different: it stores files, UID files, import sidecars, and explicitly included unsaved source drafts under a durable `deletion_id`, so `restore_assets` can work after an editor restart. Permanent deletion and purging recovery data have no Undo. Restore refuses collisions rather than overwriting existing files.

Use `get_logs` for historical editor or selected-run entries, with filters, cursors, and an optional `run_id`. Use `get_diagnostics` for a fresh validation verdict over a captured source snapshot and unsaved dependencies. Log silence or an old error does not establish current validity, and a diagnostic snapshot does not guarantee the live project stayed unchanged afterward. Operation results are retained for up to 64 records and 16 MiB per editor session, with completed records evicted first; source continuations, read bases, and snapshots have separate bounds. Missing or expired receipts are explicit errors, and editor restart clears session operation state, so inspect current files, context, and runtime state before choosing a recovery action.
